# Graph MVP — Implementation Plan

This plan layers concrete checkpoints on top of the 4-week sketch in
`../graph-mvp-sketch.md`. Each checkpoint has a sharp "done when" so you
can stop and ship at any point.

The end state: a working laptop demo where synthetic HVAC distributor data
becomes a browsable Obsidian wiki + a chat UI that answers natural-language
questions with full audit traces.

---

## Guiding constraints

- **No agent framework.** Hand-roll the loop in ~200 lines. Add a framework
  later only if a wall appears.
- **Python 3.11+** for everything except the chat frontend.
- **Single-tenant, local-only.** No auth, no multi-tenancy, no cloud.
- **CSV in, markdown + DuckDB out.** No live ERP connectors yet.
- **Templates first, LLM creativity second.** Entity pages (SKU/supplier/
  customer) are templated. LLM only writes narrative slots and concept pages.
- **Audit everything.** Every model call and tool call writes a SQLite row.

## Milestone 1 — Synthetic data + DuckDB ingest  (Week 1, ~3 days)

**Goal:** a believable HVAC distributor's operational data lives in DuckDB.

### 1a. `src/ingest/synthetic.py`
- Define the parts ontology in code (capacitors, contactors, motors,
  refrigerants, coils, control boards, thermostats — about 7 categories,
  each with 3-6 sub-types).
- Use real-feeling manufacturer names (Lennox, Carrier, Trane, Goodman,
  Rheem, York, Daikin, Mitsubishi).
- Generate:
  - 5,000 SKUs with manufacturer + category + supplier + price band
  - 20 suppliers (1-2 master distributors like Global/MARS-style)
  - 500 customers (mix of contractors / builders / property managers,
    spread across regions)
  - 4-6 warehouses
  - 24 months of orders with weekly-level seasonality
    (cooling-side spikes May–August, heating-side spikes Nov–Feb)
  - Inventory snapshots derived from orders + a synthetic restock cadence
- Write CSVs to `data/raw/`.

### 1b. `src/ingest/csv_loader.py`
- Open/create the DuckDB at `data/staging.duckdb`.
- Use `read_csv_auto` to load each table; cast types where DuckDB guesses
  wrong; declare PKs/FKs.
- Smoke-check: row counts match the CSVs.

### 1c. `scripts/generate_synthetic_data.py`
- Wraps `synthetic.generate(...)` with a `--seed` flag.

**Done when:** `python scripts/generate_synthetic_data.py` produces CSVs;
loading them gives a DuckDB you can query like
`SELECT category, COUNT(*) FROM skus GROUP BY 1` and get sensible numbers.

## Milestone 2 — Wiki compilation  (Week 2, ~5 days)

**Goal:** Obsidian opens `data/wiki/` and shows ~6k linked markdown pages
with a recognizable graph view.

### 2a. Templated entity pages — `src/compile/{sku,supplier,customer}_pages.py`
- One Jinja template per entity type (`templates/*.md.j2`, already stubbed).
- For each row, fill structured fields directly from DuckDB.
- For narrative slots (`llm_description`, `llm_notes`, `llm_concentration_summary`,
  `llm_refrigerant_summary`), call Claude (`GRAPH_COMPILER_MODEL`,
  default `claude-sonnet-4-6`) with the row + a short prompt from
  `src/agent/prompts.py::COMPILER_*`.
- Substitutes for SKU pages: pull 5-15 candidate SKUs in the same category
  with similar specs and let the LLM pick a small ranked list.
- Wikilinks (`[[skus/CAP-TURBO-200]]`) for every reference.
- Cost control: batch narratives; cache by `(template_version, row_hash)`
  in a sqlite K/V so re-runs don't re-burn tokens.

### 2b. Indexes + concept pages — `src/compile/index_pages.py`
- Per-category index (`skus/_capacitors.md`, etc.).
- Top-level `_index.md` already stubbed; regenerate links to category indexes.
- Concept pages: a small fixed list for the MVP —
  - `concepts/r-410a-phase-out.md`
  - `concepts/lennox-tariff-impact.md`
  - `concepts/supplier-concentration.md`
  - `concepts/top-customers-by-revenue.md`
  Each generated by feeding the LLM the relevant entity pages + a SQL
  summary, asking for synthesis with cited wikilinks.

### 2c. Pipeline runner — `src/compile/compiler.py`, `scripts/run_full_pipeline.py`
- Orchestrate: ingest → entity pages → indexes → concept pages →
  health check (last item deferred to milestone 3b).
- Progress bars via `tqdm`.

**Done when:** Open `data/wiki/` as an Obsidian vault. Graph view shows
several thousand nodes; clicking around reveals coherent SKU pages with
working backlinks and narrative paragraphs that read true to HVAC.

## Milestone 3 — Agent loop + tools  (Week 3a, ~3 days)

**Goal:** `run_agent("...")` returns an answer plus a trace_id, with the
agent demonstrably reading wiki pages and running SQL.

### 3a. Tools — `src/tools/`
- `read_wiki_page(path)`: validates path is inside `wiki_dir`, reads file.
- `search_wiki(query, limit)`: ripgrep against `wiki_dir`, return top
  matches with one-line snippets (cheap, no embeddings).
- `list_wiki_directory(directory)`: `os.listdir` with the same path guard.
- `run_sql(query, max_rows=200)`: open DuckDB read-only, run, return
  rows as `list[dict]`, error message on failure.
- `get_schema(table)`: `DESCRIBE` the table.

### 3b. Loop — `src/agent/loop.py`
- The pseudocode from `graph-mvp-sketch.md` §"The Core Agent Loop".
- Use `claude-opus-4-7` (per `GRAPH_AGENT_MODEL`) with `tools=AGENT_TOOLS`.
- Cap `max_iterations=15`; on overflow, return the partial answer + a
  flag in the trace.
- Every iteration: log model call, every tool call, every tool result.

### 3c. Audit logger — `src/audit/logger.py`
- Initialize SQLite from `schema.sql` on first call.
- `new_trace_id()` → uuid4.
- `log_step()` writes one row per event.
- `fetch_trace()` returns ordered events for a trace_id.

### 3d. Health check (deferred from 2c)
- A simple LLM pass: sample 30 random wiki pages, ask "anything obviously
  wrong, contradictory, or missing?" Write findings to `data/wiki/concepts/health-check.md`.

**Done when:** `python scripts/demo_queries.py` produces sensible answers
to the four canonical demo questions, and each answer's trace has the
expected mix of wiki reads + SQL queries.

## Milestone 4 — API + chat UI  (Week 3b, ~2 days)

**Goal:** open `http://localhost:8000`, ask a question, see the answer,
click "show sources", see the trace.

### 4a. FastAPI backend — `src/api/`
- `POST /chat` → `run_agent` → return `{answer, trace_id, iterations}`.
- `GET /audit/{trace_id}` → `fetch_trace` → return events.
- Mount `web/` as static.

### 4b. Frontend — `web/`
- Already stubbed: `index.html`, `app.js`, `style.css`.
- Polish: keyboard send (Enter), loading spinner, basic markdown render
  for the answer, JSON pretty-print in the sources panel.

**Done when:** the demo flow works in a real browser end-to-end.

## Milestone 5 — Demo polish + recording  (Week 4)

**Goal:** the 2-minute demo video that goes to HARDI / PE operating partners.

- Pick the 4 strongest questions; rerun until prompts and pages produce
  consistently good answers (iterate on `AGENT_SYSTEM_PROMPT` and template
  narrative prompts).
- Tighten the SKU template so substitute lists are short and confident.
- Make sure the Obsidian graph view looks visually impressive on the demo
  laptop (force-directed layout settled, sensible node colors).
- Record:
  1. Ask a tariff-exposure question, show the answer
  2. Click "show sources", scroll through the trace
  3. Cmd-tab to Obsidian, show the graph view + a SKU page
  4. Voice-over: "this whole system was built from the distributor's raw
     data in 4 weeks"
- Write the 48-hour pilot one-pager.

**Done when:** demo lands; pitch deck and pilot offer ready for outreach.

## Explicitly out of scope for the MVP

From `graph-mvp-sketch.md` §"What's Deliberately NOT in the MVP":

- Real ERP connectors (DDI / Eclipse / SX.e) — CSV only
- Multi-tenant SaaS infrastructure
- Auth / user management
- Smart model routing (Sonnet/Haiku/Together) — single model only
- Incremental wiki updates — recompile from scratch each time
- Cloud deployment beyond a single VM
- Caching for chat queries
- Embeddings, vector search, fine-tuning

Add any of these only when a real customer asks for them.

## First-week kickoff order

If you sit down tomorrow and have one week, do this in order:

1. Get `pip install` clean and `pytest` running (Milestone 0)
2. Stand up the synthetic data generator + DuckDB load (Milestone 1)
3. Get *one* SKU page generating end-to-end with templated structure +
   one LLM narrative slot (validates the compilation pattern early)
4. Scale that to all entity types (Milestone 2)
5. Build the agent loop against the existing wiki (Milestone 3)
6. Wire up FastAPI + the frontend (Milestone 4)

The riskiest piece is #3 — the LLM narrative quality and cost. Get a single
page working before scaling to 5,000.
