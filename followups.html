Future direction: "brain on a heartbeat"

The four tiers below turn the system from a reactive RAG agent (answers when asked) into a proactive one (surfaces things you didn’t ask about). They’re sequenced by effort-to-value ratio. Important: before implementing any tier, write a dedicated implementation plan for that tier — same format as the original 8-phase plan in PLAN.md. Each tier has enough surface area (scheduling, delivery, anomaly rules, memory) that diving in without an upfront plan would mix architectural decisions into feature commits and create messy phases.

Tier 1 — Scheduled proactive analysis

priority: high (best effort/value) effort: 3–5 days trigger: when you want the system to message you without prompting origin: post-Phase-8 roadmap

Run the existing daily-brief workflow + health check on a schedule, deliver to email/Slack, and add a small alerts table for threshold rules. Most of this is glue around code that already exists.

Scope:
(a) scripts/scheduler.py using APScheduler with three jobs: daily brief 7am, health check Monday 8am, ingest watch nightly. (b) src/delivery/ with one adapter (SMTP email or Slack webhook). (c) alerts table in SQLite with simple threshold rules (refrigerant exposure > $X, customer revenue drop > Y%, supplier bulletin spike). (d) "Inbox" UI tab showing scheduled-output items.
Plan first:
Write a Tier-1 implementation plan covering the scheduler choice, delivery-channel decision, alert-rule DSL shape, and Inbox UI design before any code lands.

Tier 2 — Pattern + anomaly detection

priority: medium effort: 1–2 weeks trigger: once Tier 1 is in active use and you can distinguish signal from noise origin: post-Phase-8 roadmap

Detect non-obvious patterns: "three emails this week mention R-454B pricing — looks coordinated", "customer’s R-410A exposure crossed the SOP’s retrofit-outreach threshold", "TSB-2024-007 contradicts the inventory reorder policy". Hard to get right — false positives become noise. Ship rule-based detection first; layer LLM-judged signals only on candidates the rules surface.

Scope:
(a) Rule engine over DuckDB + retrieval results (cron + SQL diffs + chunk-cluster scans). (b) Per-rule confidence scoring. (c) An "anomalies" feed in the Inbox UI. (d) Optional LLM judge gate to suppress weak signals.
Plan first:
Write a Tier-2 implementation plan that nails down the rule DSL, what counts as a baseline, and the false-positive containment strategy (mute rules, confidence thresholds, user feedback loop). Skipping this plan is how anomaly systems become noise machines.

Tier 3 — Recommendations + autonomous action

priority: low until Tier 1+2 are dialed in effort: 3+ weeks trigger: when Tier 2 anomalies are trustworthy enough that the next step is "and then what" origin: post-Phase-8 roadmap

The system chains detection → action: "Carrier sent a tariff email; want me to run the tariff-response workflow and draft customer comms?" "Customer Z hit your retrofit threshold; here’s a draft outreach email." High lift because it needs guardrails (draft, never send), a decisions/audit table, and observability so the user trusts what the system is about to do.

Scope:
(a) Decision-policy layer that maps anomalies → recommended workflows. (b) "Draft mode" by default — no autonomous external action. (c) Approval UI: every recommendation shows the rationale, draft output, and an approve/dismiss flow. (d) Outcome tracking so we can measure recommendation quality.
Plan first:
Write a Tier-3 plan covering the decision policy, the guardrails, the approval UX, and the outcome-tracking metric. Anything here that runs without explicit approval is a liability — the plan is where we draw the line.

Tier 4 — Memory + learning

priority: low (long game) effort: 2+ weeks initial, ongoing accrual trigger: once there’s ~3+ months of audit-log history to learn from origin: post-Phase-8 roadmap

"You asked this last week; here’s the diff." "You decided pass-through on Carrier 30 days ago — has revenue held?" "These are the questions you ask every Monday — want them auto-surfaced?" Cheap to start (the audit log already has the data), valuable once accumulated.

Scope:
(a) Question-history index over the audit log with semantic clustering. (b) Decision-tracking table for workflow outcomes. (c) "What changed since last week" diff workflow. (d) Personalized morning-briefing that picks up on the user’s pattern of questions.
Plan first:
Write a Tier-4 plan covering the memory schema, what counts as a "decision," the diffing strategy, and how personalization avoids creepy. The audit log gives us the raw material; the plan tells us what to do with it.
