Phase 2 — Source corpus

Design decisions decision

  • Manifest is auto-built, not hand-edited. Every markdown source carries YAML frontmatter declaring its manifest entry. Every non-markdown source (jsonl, csv) has a sidecar <name>.meta.yaml next to it. scripts/generate_corpus.py walks the tree, harvests these, and writes data/sources/manifest.yaml. Adding a new source means dropping a file into the right bucket with frontmatter — never hand-editing the manifest. Re-build at any time with --manifest-only.
  • Hand-authored "showcase" set + generator-bulk. 11 docs are hand-authored to be high-quality demo material (4 regulatory bulletins, 3 manufacturer TSBs, 6 SOPs, 2 supplier email threads, 1 install-procedure manual). The remaining ~60 are produced by deterministic template-based generators in scripts/generate_corpus.py. Hand-authored docs cross-reference each other with wikilinks so demo workflows hop between them naturally.
  • Generators are pure Python templates, not LLM calls. Generating bulk content via the Anthropic API would cost real money on every regeneration and would not be deterministic across runs. The templates produce plausibly-messy text without the API. The cost: less surface-level variety than an LLM would produce. The benefit: free, reproducible, hermetic.
  • Real-anchor strategy: reference-only with a fetcher. Three real public regulatory docs (EPA AIM Act final rule, EPA SNAP Rule 23, DOE residential CAC rule) are declared in the manifest with license: reference-only and a fetch: URL. They are not checked into the repo. scripts/fetch_anchors.py downloads them on demand into data/sources/bulletins/. The pipeline will treat their absence gracefully — the manifest entry exists so retrieval traceability is preserved, but ingestion skips missing files.
  • Tickets are JSONL, one Document per record. Four ticket files cover four time periods, each with 9–12 records. The manifest lists each file with a record_count field; the eventual loader (Phase 3) will emit one Document per record, so a single manifest entry expands to multiple retrievable Documents. This keeps the manifest readable while satisfying the per-record citation requirement.
  • Cross-references use wikilinks, not relative paths. Hand-authored bulletins and SOPs link to each other as [[bulletins/r-410a-phase-out-timeline]], mirroring the Obsidian-vault convention used elsewhere in the project. The structurer in Phase 5 will resolve these against the generated wiki; the ingestion pipeline in Phase 3 will preserve them as text so retrieval can follow them.
  • Per-bucket file layout matches the manifest's bucket field 1:1. A source's bucket is harvested from frontmatter, but if missing the manifest builder falls back to the parent directory name. This keeps the convention robust to forgetting the field.

Tradeoffs tradeoff

  • Frontmatter-as-manifest vs. central manifest file. Central-file pros: one place to read everything, no walking required. Frontmatter pros: adding a source can never desynchronize from the manifest, manual-authoring is easier (no separate file to keep up to date), and the generator and the human use the same convention. Picked frontmatter. The walk is fast at 75 files.
  • Sidecar .meta.yaml for non-markdown vs. embedding metadata into the file. Could embed in JSONL header records or CSV comments, but those break the loader's record schema. Sidecars keep the data file pure and put the metadata in a clearly-distinct file. The sidecar is named <file>.meta.yaml so the relationship is obvious and the manifest builder's discovery is trivial.
  • Real anchors: download script vs. check in. Checking in EPA PDFs would be operationally easier but legally murky for a portfolio repo. The fetcher gives the same demo experience (a few seconds of network on first run) without the redistribution question. If the URLs rot, the fetcher reports the error and the manifest entries still document what should be there.
  • Deterministic templates vs. LLM-authored synthetic. See decisions. Tradeoff is variety/realism vs. cost/reproducibility. For a portfolio piece where the corpus needs to look the same every time a reviewer clones, deterministic wins.
  • Number of hand-authored docs. Considered authoring 20+ showcase docs; settled on 11. Each hand-authored doc gets a meaningful share of demo time, so 11 is enough to seed the key workflows (refrigerant exposure, supplier risk, tariff response, daily brief). More would have padded the corpus without raising demo quality.

Phase 3 — Ingestion pipeline

Design decisions decision

  • Loader dispatch lives in loaders/base.py (load_for_entry()) rather than in the ingest driver. Keeps the driver dumb and lets tests exercise the dispatch directly.
  • Per-loader "Document" boundary policy:
    • Markdown / PDF / CSV: 1 Document per file. Frontmatter stripped (markdown), rows rendered as a markdown table (CSV), page offsets recorded (PDF).
    • Email: 1 Document per message within a thread. The thread's source_id is suffixed with #msg-{n} so each message is independently citable. Headers are normalized and rendered into the content so retrieval can hit on From: / Subject: tokens.
    • Ticket: 1 Document per record in the JSONL file. Source_id suffixed with #{ticket_id}.
  • Chunker is heading-aware recursive. Parses markdown into a section tree, then walks: if a section (heading + body + descendants) fits within max_tokens (1000) it's emitted whole; otherwise the section's own body is emitted first and the walker recurses into children. Leaf sections bigger than max_tokens fall back to paragraph-with-overlap splitting. Adjacent small siblings with a shared heading-path prefix are combined to keep chunks dense (target ~700 tokens).
  • Token counting uses tiktoken cl100k_base. Not exact for Voyage but close enough for sizing decisions; avoids dragging in Voyage's tokenizer (which would force the Voyage SDK as a hard dep).
  • Chunk IDs are content-hashed. Format: {source_id}:{ordinal:04d}:{short_hash}. Re-ingesting unchanged content produces the same chunk_id — important for the freshness logic in Phase 5.
  • Index idempotency is source-scoped, not chunk-scoped. When you re-ingest a source, index_chunks deletes every existing row for that source_id first, then inserts the new chunks. This guarantees no orphans when a source's content shrinks. The downside: a re-index always rewrites; we don't take advantage of unchanged-chunk skips at the LanceDB layer. For an 86-source corpus that's fine; re-evaluate if we ever cross ~10K sources.
  • BM25 corpus is rebuilt from LanceDB after every ingest. Pulls every row and pickles the BM25 + chunk-id mapping to data/bm25.pkl. Simpler than maintaining BM25 incrementally and the cost is sub-second at this corpus size.
  • Filterable columns hoisted out of metadata. LanceDB has first-class typed columns for bucket, source_type, and manufacturer on top of the full metadata-as-JSON column. Lets Phase 4's filtered retrieval do WHERE bucket = 'bulletins' directly instead of post-filtering Python.
  • Metadata enrichment is pattern-first, LLM-optional. A curated vocab of manufacturers / refrigerants / regulations / SKU-ID patterns runs as a regex pass over every chunk. Free, deterministic, covers ~90% of the cases the LLM would catch because the entity universe is small and well-defined. The Haiku LLM pass is opt-in via --llm-enrich and is cached by content hash; useful for long-tail mentions and inferred doc_type but not needed for Phase 3's done-criterion.
  • Audit logging at the ingest level. One trace_id per ingest run. Events logged: ingest_started, source_indexed per source, source_missing / source_empty / load_error for skips, ingest_complete with totals. Same SQLite log the agent loop writes to — Phase 4's UI can show ingest history alongside chat traces with no new infrastructure.

Deviations deviation

  • Voyage embeddings are optional, with a hash-pseudo-vector fallback. The spec said "Voyage-3 embeddings." But the user's .env has no VOYAGE_API_KEY, and the same will be true for any reviewer who clones the repo. Hard-requiring Voyage would block clone-and-run. So embed.py checks for the key at call time: if present (and the optional voyageai dep installed) it uses Voyage; otherwise it generates deterministic L2-normalized vectors from SHA-256 of the chunk content. These pseudo-vectors are not semantically meaningful — hybrid retrieval in Phase 4 will degrade to BM25-only behavior until a real key is set. A loud warning prints once per process. Voyage is now in [project.optional-dependencies].voyage; install with pip install -e .[voyage].
  • Added tiktoken as a hard dep on top of the Phase 3 plan's listed deps. The chunker needs a tokenizer; tiktoken is small and standard. Calling token counting "approximate" via character count (as the original chunker docstring suggested) would have given wildly inconsistent chunk sizes.
  • Added index_stats() helper on top of the plan's index_chunks / drop_index API. Used by the ingest driver's run summary and slated for Phase 7's Ingest UI.
  • Email loader emits per-message Documents. The Phase 1 module docstring described this behavior; the Phase 3 spec didn't explicitly re-mandate it. Sticking with per-message because it lets retrieval cite a specific sender + date instead of an entire thread, which is the demo-defensible behavior.
  • Reference-only anchors are skipped silently when missing. If a manifest entry has license: reference-only and the file isn't on disk (i.e. fetch_anchors.py hasn't been run), the loader returns an empty list and the driver logs source_missing. No error. Three anchors were in this state during the smoke run.

Tradeoffs tradeoff

  • Combine-adjacent-siblings chunker policy. Considered chunking purely by max-size with no combination. Result would have been many short chunks and many redundant retrievals for short documents (every SOP would become 3-4 chunks). Picked combining because the corpus skews short (most docs < 1000 tokens) and dense chunks give the agent more context per retrieve() call. Cost: a single 700-token chunk is a coarser citation than a 200-token one. If retrieval evals in Phase 8 show citation precision suffering, drop target_tokens to 400 and let the combiner produce smaller chunks.
  • Page-range derivation from char offsets. PyMuPDF gives per-page text; the loader concatenates with \n\n joiners and records each page's starting char offset. The chunker computes a chunk's page range by binary-positioning its char_range against the offset table. Cheap and good enough for citations. Off by 1 page in rare cases where a section spans the join boundary.
  • BM25 in-process via rank_bm25. Alternatives: Tantivy (faster, Rust, harder install), Elasticsearch (overkill), DuckDB FTS (would unify with our DuckDB layer but requires extra extension setup). rank_bm25 is pure Python, zero infra, fits the local-first goal. At 117 chunks the search is instant; would re-evaluate around 100K chunks.
  • Pattern-first metadata enrichment vs LLM-always. See decisions. The spec said "LLM-assisted enrichment (Haiku)." I kept the LLM path (cached, opt-in) but made it optional. Reason: the entity universe is bounded (12 manufacturers, 5 refrigerants, ~7 regulation slugs) and a regex catches them deterministically. Charging API credits for re-ingesting an unchanged corpus would be a bad default.
  • Markdown loader does not parse the heading tree. The chunker owns the parse instead. Reduces duplication and keeps the loader trivially simple. The chunker already needs to walk headings for splitting; making it the single owner avoids two slightly-different parses drifting.

Phase 4 — Hybrid retrieval + new tools

Design decisions decision

  • Per-trace citation registry, allocated at the tool-wrapper layer. search.retrieve() returns RetrievedChunk with citation_id=""; the agent tool wrapper in tools.py allocates ids (c1, c2, ...) from a CitationRegistry living on the ToolContext. This means (a) the search function stays pure and reusable outside the agent loop, (b) citation ids are stable across multiple retrieve() calls in the same conversation (re-retrieving the same chunk returns its existing id, not a new one).
  • Tool context is threaded explicitly, not via contextvars. execute_tool(name, args, context) takes the context as a parameter. Considered contextvars for less plumbing; rejected because explicit threading is more readable and the agent loop is the only caller. The parameter defaults to None so existing direct callers (e.g. tests) work without changes.
  • Hybrid scoring: min-max per channel, weighted sum, alpha = 0.6. BM25 and vector cosine produce wildly different score scales; combining them raw would let one channel dominate. Min-max-normalizing each channel onto [0,1] makes the alpha weight do what the docstring says. Default alpha = 0.6 tilts toward semantic; revisit if Phase 8 evals say otherwise.
  • First-class filter columns hoisted into LanceDB SQL where clause. bucket, source_type, manufacturer, source_id are typed columns and get pushed down. refrigerant, date_from, date_to live in the JSON metadata blob and are post-filtered in Python. Worth it because most filtered queries in the workflows use bucket/manufacturer.
  • Voyage rerank is optional and auto-detected. rerank=True is the default; if VOYAGE_API_KEY is unset the rerank step silently no-ops. The combined-score ordering carries through unchanged.
  • Citation extraction is regex-based on the final answer text. The loop scans for [cN] tokens after the model returns end_turn, de-duplicates, and returns only ids that were actually allocated by retrieve() in this trace. Hallucinated [c99] citations are dropped silently.
  • UI citations: inline link + dedicated list below the answer. Each [cN] renders as a styled badge that scrolls to and flashes a matching card in a "Citations" list at the bottom of the message. Considered a hover popover; deferred (see follow-ups). Click-to-scroll-and-flash is simpler and meets the done-when.
  • System prompt rewritten to describe three sources of truth + citation discipline. Old prompt only knew about wiki + SQL. Deviations deviation

  • Did not write a new end-to-end agent test. The .env has ANTHROPIC_API_KEY=sk-ant-... (placeholder), so running the agent loop against the real API isn't possible from this environment. Phase 4 was verified by smoke-testing every layer except the model call: tool schemas registered, citation registry allocates and dedups correctly, citation extraction de-duplicates and drops hallucinated ids, retrieve tool formats correctly, read_source handles missing/anchor cases, FastAPI app loads. The model-in-the-loop path will work the first time you run the UI with a real key; if it doesn't, the audit log will tell us exactly where.
  • The retrieve tool output is text-formatted, not JSON. The spec didn't specify the format. Other tools (run_sql, get_schema) return JSON. retrieve returns a human-readable block with [c1] source_id headers and snippets because (a) it's what the model has to read, and (b) the format puts the citation id right next to the content it cites, which makes the "cite as [c1] in your answer" rule visually obvious. JSON would have buried the ids inside a nested structure.
  • No new tests added for the loaders / chunker / index in tests/. Phase 3 came in lint-clean and smoke-tested via the ingest run, and Phase 8's golden-set evals will exercise the entire pipeline end-to-end. Writing a unit-test suite now would duplicate that future coverage. Existing tests still all import cleanly.
  • Citation rendering uses a plain string replace on the rendered HTML. Technically fragile — if the markdown renderer ever emitted [c1] inside a <code> block, my replacement would still convert it into a clickable link inside the code block. Today our markdown renderer doesn't escape brackets that way and the model is unlikely to put citations inside fenced code, but flagging because it's a known sharp edge.

Tradeoffs tradeoff

  • Citation id allocation: per-trace vs per-call. Per-call would give c1 a different meaning in each retrieve, which is confusing for the model and breaks the "click [c1] to see the chunk" UI contract. Per-trace keeps ids stable for the whole conversation. Memory cost is negligible (one dict per trace, garbage-collected when the trace finishes).
  • Snippet picking: simple substring match around the first query token vs. proper highlight extraction. Picked simple. Good enough for citation cards in the UI; the model gets the full chunk in the tool result, not just the snippet, so model behavior isn't affected.
  • Score normalization: min-max vs reciprocal rank fusion (RRF). RRF is the more famous hybrid-retrieval combiner. Picked min-max because it preserves continuous score values (useful for citation-card display and reranker tiebreaking), is debuggable without an extra fusion concept, and works fine at this corpus size. Switch to RRF if it ever beats min-max in evals.
  • Read_source vs read_wiki_page surface overlap. Both let the agent read prose. Kept them separate because they hit different layers: read_source for raw ingested documents (cited via [cN]), read_wiki_page for the LLM-built wiki (cited prose-style). The system prompt explains which to use when.

Phase 5 — Knowledge structurer

Design decisions decision

  • Default scope: only the NEW entity types this phase introduces. Concepts.yaml declares seven entity types but four of them (skus, suppliers, customers, plus any future additions) already have pre-Phase-5 template-rendered pages from the original MVP. Rebuilding all 5,520 of those with LLM synthesis would cost real money on every run. The builder defaults to NEW_ENTITY_TYPES = {refrigerants, regulations, manufacturers, procedures} — about 32 pages — and only rebuilds the existing ones when --include-existing is passed (or they're named via --only).
  • Two synthesis paths, picked at runtime. If ANTHROPIC_API_KEY is set, the builder uses Sonnet to synthesize prose with inline [chunk_id] citations. Otherwise it falls back to a deterministic composer that lays out the retrieved chunks under each required section as block-quoted snippets with bracketed citations. The deterministic page is honest about its limitations — the frontmatter records synthesizer: deterministic and the page body has a header note "This page was assembled without LLM synthesis." Same mechanism as the embed-fallback pattern from Phase 3.
  • Page-build cache keyed by (entity_id, sorted chunk_ids, template version). SQLite at data/structure_cache.sqlite. Re-running with no source changes is free. Cache key uses the sorted chunk_id list so semantic equivalence beats source-order changes.
  • Chunk_id citations, not chunk-text-hash citations. Phase 4's citation tool produces transient c1/c2 ids that are per-conversation; the structurer needs persistent ones that survive across runs. Chunks already have stable content-hashed ids from Phase 3 ({source_id}:{ordinal:04d}:{short_hash}) so the page cites those directly. The wiki frontmatter's source_chunks: [...] list is the same id space; freshness uses it to detect when the supporting evidence has changed.
  • Validation: post-generation, regex over [chunk_id]. The builder checks every cited id is in the retrieved set (model can't invent ids) and warns if the page contains no citations at all. Warnings travel to the page frontmatter (validation_warnings: [...]) and surface in the health check.
  • Validation is non-blocking. A page with warnings still gets written. The alternative (refuse to write) would mean a hallucinated citation blocks the whole entity. The wiki being merely imperfect is more useful than the wiki being missing. The health-check tab surfaces warnings so problems aren't invisible.
  • Freshness detects stale pages via two signals only. (a) Any cited chunk_id no longer exists in the LanceDB index, (b) the page's template_version is below the builder's current version. We don't separately model "chunk content changed" because chunk ids are content-hash-derived — a changed chunk has a new id and the old id is gone. This collapses two signals into one.
  • Health check covers six dimensions. Orphan chunks (indexed but not cited anywhere), thin pages (< 2 chunks), dangling wikilinks, validation warnings from the builder, optional LLM contradiction detection, and coverage-by-bucket (cited unique chunks ÷ total chunks per source bucket). LLM contradiction detection is opt-in via --health-llm.
  • Health report writes to data/wiki/concepts/health-check.md. Returned to callers AND rendered as a wiki page so it shows up in the Obsidian view and (eventually) in the Phase 7 admin tab.
  • Rerank disabled by default in batch builds. builder._build_one calls retrieve(..., rerank=False). Reranking 32+ entities would burn Voyage credits with limited benefit at this corpus size. Easy to flip on if Phase 8 evals show rerank materially improves citation quality.

Deviations deviation

  • Jinja2 templates listed in concepts.yaml are NOT used. Phase 1's open-items log already flagged that templates like refrigerant.md.j2, regulation.md.j2, etc. don't exist on disk. Going through with Jinja would mean (a) authoring four templates that the LLM would then have to fill, and (b) double-handling structure: Jinja owns sections and the LLM owns prose inside them. Cleaner: the system prompt and required_fields directly specify sections, the LLM writes the whole page, validation enforces structure. The template field is preserved in concepts.yaml and surfaces in frontmatter as template_name but is not load-bearing for the build. Followups item resolved by replacement.
  • Did not exercise the LLM synthesis path live. Same reason as Phase 4: .env has a placeholder ANTHROPIC_API_KEY. Verified the LLM path imports cleanly, the prompt builds without errors, and the cache writes work. The first real --no-llm-off run with a live key is the integration test. Followups item already covers this from Phase 4.
  • The deterministic fallback's section matching is loose. Pages get required_fields as H2 section headers; the fallback picks chunks whose heading_path contains the field name (case-insensitive substring). For most fields this works, but specific ones like "Retrofit Options" don't match any chunk heading, so those sections come out empty with "_No source coverage._" The LLM path doesn't have this limitation because it synthesizes prose from any chunk. Acceptable tradeoff: the deterministic page is explicitly stub-tier.
  • No new concept pages built (yet). concepts.yaml has the four NEW entity types but doesn't include the cross-cutting concept pages (R-410A phase-out exposure, supplier concentration, top customers) from the original MVP. The structurer's pattern supports them — would just need a "concepts" entry in concepts.yaml with a static instance list — but the existing concept pages already exist as hand-authored prose. Adding "concepts" as a fifth NEW type is a one-line YAML addition + a re-run, deferred to followups.
  • Dangling-wikilinks count is high (45) and mostly benign. Hand-authored sources reference wiki targets like [[suppliers/]] (an index) and [[manufacturers/Lennox]] that don't resolve as exact paths because the wikilink resolver is strict. The health check reports them honestly. Not a code bug — a content-organization opportunity. Flagged to followups.

Tradeoffs tradeoff

  • Build scope: 32 new pages vs 5552 (everything). Considered defaulting to --include-existing. Cost-prohibitive for live LLM runs and would replace working SKU/supplier/customer pages with potentially worse output. Default-new keeps the demo fast (~0.2s deterministic, ~2 min with LLM) and lets the user opt in to the bigger rebuild when they want.
  • One generic synthesis prompt vs per-entity-type prompts. Per-entity-type would tune content shape (a manufacturer page wants product categories + regulatory posture; a regulation page wants effective dates + affected equipment). One prompt with required_fields as the dispatch keeps the code simple at the cost of generic prose. Easier to specialize later if eval quality lags.
  • Page-level cache vs no cache. No cache would make every build full-cost. Cache + --force for explicit invalidation matches the existing narrative-cache pattern (Phase 2 MVP) and lets re-runs of the same source state be free.
  • Health check as one big walk vs incremental. Built it as one walk over all pages + all chunks. At 32 pages and 117 chunks it's milliseconds. If the corpus grows past ~10K chunks I'd want an incremental version that tracks deltas against the last run.
  • Contradiction check: per-entity-type vs all-pages-at-once. Picked per-type: ask the LLM to compare among same-entity pages (e.g. all manufacturer pages together). Catches the most likely contradiction class (two manufacturer pages disagreeing on a manufacturer's refrigerant posture). All-pages-at-once would catch cross-type contradictions but cost more tokens and dilute signal.

Open questions open

  • LLM path unexercised. Same blocker as Phase 4. Tracked in followups.
  • Add "concepts" as an entity type in concepts.yaml? Would let the structurer rebuild the cross-cutting concept pages with citations. Currently those pages are hand-authored from the original MVP — adding the structurer to the loop is a tiny YAML change. Deferred.
  • 45 dangling wikilinks in the corpus. Most are [[suppliers/]] (index-style references) and similar in hand-authored sources. The health check reports them; could either (a) fix by creating index pages in data/wiki/ or (b) loosen the resolver to treat trailing-slash links as directories. Followups.
  • Validation could be stricter — currently checks that no [chunk_id] is invented but doesn't enforce that every claim has a citation (would need claim-splitting). Phase 8 eval's unsupported_claims metric will measure this; tighten if numbers are bad.

Phase 6 — Ops-lead workflows

Design decisions decision

  • Workflows are server-side bundles, not client-side prompts. Each Workflow declares a parameter schema + a prompt template. The UI GET /workflows to fetch the schemas and renders a form; the backend formats the prompt and runs the agent. This keeps prompt tuning a server-only change (no client deploy) and centralizes parameter validation.
  • Workflows ride the existing agent loop. POST /workflows/{slug}/stream just constructs a user message from the parameters and yields events from stream_agent(). Workflows inherit streaming, audit, tool use, citations, and the retrieve/read_source contracts for free. No parallel orchestrator.
  • Parameter types: choice, string, number. Enough surface to cover all four workflows without inventing a form-builder DSL. Coercion + validation in runner._coerce; bad input raises WorkflowError which the API maps to 400.
  • Free-text supplier and manufacturer inputs, not enumerated choices. Workflows could pre-populate dropdowns by enumerating SELECT name FROM suppliers from DuckDB. Skipped — keeps the UI simpler and retrieval's substring-match on the manufacturer column is robust to short forms ("Lennox" vs "Lennox PartsPlus"). Followups item flagged in case you want enum dropdowns later.
  • Derived prompt fields computed in the runner, not the workflow definition. Some templates need values that aren't direct parameters (e.g. the refrigerant slug "r-410a" for wiki path lookup, or a SQL fragment conditioned on whether a category was passed). _derived_fields() computes these per workflow slug — small, explicit, easy to grow.
  • Four named workflows match the plan exactly:
    • refrigerant-exposure — refrigerant + top_n → SQL + retrieve + actions.
    • supplier-risk-review — supplier + optional mfr → concentration + signals + substitutes.
    • tariff-response — manufacturer + magnitude + optional category → exposure + pricing decision + outreach.
    • daily-brief — no params → standing 4-section brief.
  • Prompts steer tools explicitly. Each workflow's prompt says which tools to call in which order ("Run a DuckDB query…", "Retrieve regulatory context…", "Read the wiki page if one exists"). Counter-pattern to "let the agent figure it out" — the workflows are pre-canned recipes, so the prompt should encode the recipe.
  • Same daily-brief prompt is used in two places. The standalone brief generator (src/briefs/generator.py) writes to data/briefs/YYYY-MM-DD.md as a file artifact; the workflow returns the answer in-conversation. Both prompts were updated to use [cN] citations + drop the PE-pitch framing in favor of "business owner / ops lead." The two prompts are not shared via import — they're close cousins kept locally because the standalone brief might evolve differently (it's headed for an email-delivery path).
  • UI: workflows drawer alongside the existing briefs drawer. Reuses the drawer + scrim plumbing already in place. Workflow cards have inline parameter forms (no second-step modal). Submitting a card closes the drawer, appends a "Workflow · {title}" user message, and runs the standard streaming renderer — citations, sources panel, audit trace all work identically.
  • Shared SSE reader for chat + workflows. Refactored streamChat into streamSSE(url, body, renderer). streamChat and streamWorkflow are 1-line wrappers. Avoids two near-identical SSE parsers drifting.

Deviations deviation

  • Workflow runs are NOT logged with a dedicated audit kind. They go through the normal trace log as if a user typed the formatted prompt. The SSE stream emits a workflow_started prefix event with slug + prompt so the UI knows the trigger, but the audit DB doesn't separately record "this trace was a workflow." If we want a "show me all workflow runs of {slug}" view in Phase 7, we'd add a tag column to trace_steps or a separate workflow_runs table. Skipped because the audit trail is already complete (user_question event contains the formatted prompt, which is grep-able).
  • Did not exercise workflow runs with a live model. Same blocker as Phases 4/5. The runner and API were smoke-tested at the layer below the model call: parameter coercion works, prompt formatting works, route mounts, OpenAPI schema renders. First live run validates the model actually follows the recipe.
  • Daily-brief workflow's prompt differs slightly from the standalone generator's. The workflow version says "under 500 words" and explicitly references citation discipline; the standalone version (also updated this phase) is similar but standalone-flavored. Not a deep difference — both pull the same data — but they will drift unless we consolidate, and consolidation isn't worth a shared module today.

Tradeoffs tradeoff

  • Server-side workflow definitions vs. client-side. Client-side would mean the UI owns prompt strings and the backend is just POST /chat. Simpler API surface. But (a) prompt iteration would require client redeploys, (b) parameter validation would live in two places, and (c) the workflow concept couldn't be reused by a CLI / scheduled job. Server-side wins.
  • One generic runner vs per-workflow handlers. Per-workflow handlers would let each workflow do custom orchestration (e.g. pre-fetch data, post-process the agent output into a JSON shape). For the four workflows in scope, the prompt is enough — they all want a markdown brief with citations. Add per-workflow handlers if a future workflow needs structured output (e.g. "return a JSON of {customer_id, retrofit_quote_url}").
  • Drawer-based workflow picker vs dedicated page. Drawer keeps the existing chat front-and-center; a dedicated page would make workflows feel more first-class but split the UI into modes. Drawer fits the "workflows are shortcuts, chat is the main thing" mental model.
  • Free-text vs enumerated suppliers/manufacturers. Enumerated dropdowns would give a discovery affordance ("what suppliers can I pick?"). Free-text is one less DuckDB round-trip on drawer open + tolerates the supplier-vs-manufacturer name fuzziness that's already baked into the retrieval filter. Flagged the enumerate option as a followup.
  • Workflow prompts steer tools vs trust the agent's choice. Could have said "answer this question:" and let the agent pick tools. Picked recipe-style ("step 1: run SQL X; step 2: retrieve Y") because the demo value of workflows comes from reliable, repeatable structure. The agent retains judgment within each step.

Open questions open

  • Workflow live-run not exercised. Same as Phase 4/5 — needs a real ANTHROPIC_API_KEY. The existing "End-to-end agent run" followup item covers it but workflows add a layer worth re-validating: does the model follow the recipe, do citations come back, do the parameters interpolate as expected?
  • Enumerated dropdowns for supplier / manufacturer. See followups.
  • Should a workflow run be a special audit-log kind? Today they're indistinguishable from chat traces. If you want "list all workflow runs of refrigerant-exposure this week" later, we'd add a workflow_slug column to the audit table. Skipped now.
  • Daily brief: workflow vs file artifact. Workflow returns in-chat; the standalone generator still writes data/briefs/{date}.md on demand. Both have a place (chat = interactive, file = inbox-deliverable). If we ever wire email/Slack delivery (IDEAS.md item #B), the file artifact is the path; the workflow is the rehearsal.

Phase 7 — UI polish

Design decisions decision

  • One Admin drawer with three tabs, not three separate drawers. Ingest / Knowledge health / Evals all surface admin-flavored data; keeping them in one drawer matches the spec's "tab" language and avoids three more buttons cluttering the top bar. The drawer is wider than the others (max-width 880px) because the tables need horizontal room.
  • Backend ``/admin/*`` endpoints are read-only and live-computed. No caching layer — running the health check on every request is sub-second at the current corpus size; /admin/sources walks LanceDB once per call. Worth revisiting if a tab feels sluggish (it won't, today).
  • Sources tab data model: manifest entry + on-disk-status + chunk count from LanceDB + last-indexed timestamp from the audit log. Three sources joined at request time keeps the tab honest — a "missing" file or a never-indexed source shows up exactly as it is, no stale view.
  • Health tab is essentially a UI for the structurer's HealthReport. Runs run_health_check(use_llm=False) on each tab activation. Coverage-by-bucket gets a table; thin pages, dangling wikilinks, validation warnings, and orphan chunks each get a list (first 30, with "and N more" footer). LLM contradiction detection is an opt-in ?use_llm=true query param — no UI toggle yet (see followups).
  • Evals tab gracefully handles the no-runs case. Phase 8 hasn't built the eval harness yet, so data/evals/ doesn't exist. The tab detects that and shows a hint pointing at scripts/run_evals.py instead of failing or showing a blank table. Once Phase 8 writes summaries there, the same tab populates with no code changes.
  • Inline citation popover is a custom positioned tooltip, not the browser title attribute alone. Browser titles are slow to appear, don't render HTML, and look like OS-default cruft. The custom popover is a single appended <div> that follows the hovered link, shows source_id + heading path + snippet with proper styling, and clamps to the viewport so it doesn't fall off the right edge. title is kept as a no-JS fallback.
  • "Open source" button on every citation card. Fetches /admin/source/{source_id} (which wraps the existing read_source from Phase 4) and expands the full raw document body into a collapsible <pre> beneath the card. Loaded lazily, toggleable. Same source_id semantics as the agent's read_source tool, so the user can see exactly what the model could have read.
  • Tab state is cleared on each drawer open. Closing and re-opening the drawer resets to the Ingest tab. Simpler than persisting state across opens; the cost is one re-fetch of the source list. Cached server-side responses keep this cheap.

Phase 8 — Evals + writeup

Design decisions decision

  • Ground truth at source level, not chunk level. Phase 3's chunk_id format embeds a content hash, so any source edit invalidates all its chunk ids. Using chunk ids as golden-set ground truth would mean re-curating after every corpus tweak. expected_source_ids stays stable across content edits — the metric measures "did retrieval surface chunks from any expected source?"
  • Two runner modes: retrieval and agent. Retrieval-only calls retrieve() directly and scores recall@5/@10 + MRR. No API key, no agent — fast, free, runnable by any reviewer. Agent mode runs the full loop and adds citation precision / recall + latency + token cost. Both write the same JSONL shape and the same summary.json, so the Phase 7 Admin → Evals tab displays whichever ran.
  • Per-question + aggregate metrics. PerQuestionScore captures the full picture for one question (expected, retrieved, cited, RR, recall@k). MetricsSummary aggregates. Per-question records ship inside the summary file's by_qid array so the UI can show drill-downs without a second request.
  • Golden-set size: 30 questions. Lower end of the spec's 30–50 range. Carefully chosen to cover all four workflow areas (8 refrigerant/regulatory, 6 SOP, 5 supplier/tariff, 5 technical TSB, 3 install procedure, 3 regulatory deep-cuts). 30 is small enough to hand-audit each retrieval result; expanding is a future-iteration knob.
  • Cost roll-up uses Sonnet 4.6 list prices. $3/1M input, $15/1M output. Hardcoded into metrics.py as a documented approximation — the eval cost summary is informational, not a billing surface.
  • Idempotent eval runs with timestamped run_ids. Default run_id = YYYYMMDD-HHMMSS-{mode} so back-to-back runs don't clobber each other. Override with --run-id if you want a stable filename for CI.
  • Latency p50/p95 computed from time.perf_counter wall-clock. Retrieval-only mode times the retrieve() call; agent mode times the full run_agent() round-trip. p95 via linear interpolation, not the simpler rank-based percentile, so small sample sizes still give meaningful numbers.
  • Token usage pulled from response.usage in agent mode. Already in the audit log per-iteration; we just sum across the trace. _retrieved_from_trace() walks the same audit log to recover which sources the agent's retrieve calls returned (so retrieval scoring works in agent mode too).
  • Portfolio README is the writeup deliverable. Rewrote README.md top-to-bottom with: skill-matrix table at the top, architecture ASCII diagram, latest eval table with real numbers, quick-start, layout, key decisions pointer to implementation-notes.html and followups.html. No standalone "portfolio doc" — the README is the portfolio doc.

Deviations deviation

  • LLM-judge claim coverage is not implemented. The plan listed "claim coverage via LLM-judge, unsupported-claim count." Both fields are reserved in MetricsSummary as None. Building the judge needs (a) a live API key and (b) a claim-splitter prompt that's its own small project. Phase 8's done-when explicitly requires "evals run reproducibly" + "portfolio README" — both achieved without LLM-judge. Flagged as a followup; the rest of the eval surface is real.
  • No CI integration. Considered wiring run_evals.py into a pytest pin or GitHub Action that fails if recall@5 drops. Skipped because (a) there's no CI infrastructure to drop the action into yet, (b) regression-pinning makes more sense once we have multiple runs to compare against. Cheap follow-up: add a baseline summary file under tests/eval/baseline.summary.json and assert `recall@5 >= baseline.recall@5 - 0.02` in pytest.
  • The chunk-level retrieved-from-trace parser uses a regex on the tool-result preview. The retrieve tool's output text starts each chunk line with [cN] source-id-here. _retrieved_from_trace grabs source ids from that text. Brittle: any prompt change to the retrieve tool result format will break it. Acceptable: that format is tested in Phase 4 smoke and the eval runner is the only consumer. If we change the format, this parser updates with it.
  • Demo GIF / video is not produced. The plan listed it. Producing one requires a UI recording session against a live agent, which needs an API key. README has a layout ready for it (no placeholder yet — adding when there's a real recording). Tracked in followups.

Tradeoffs tradeoff

  • Retrieval-only as the default mode. Considered making agent mode default since it's more comprehensive. Picked retrieval-only because (a) any reviewer cloning the repo can run it without an API key, (b) the metrics it produces are real and directly comparable across configurations (BM25 only vs hybrid vs hybrid+rerank).
  • Reciprocal Rank vs Average Precision. MRR is one number per question (rank of first relevant), AP averages precision across all relevant ranks. With most golden records having 1–2 expected sources, AP collapses to MRR-with-extra-ceremony. Picked MRR for readability.
  • Hand-author the golden set vs LLM-generate it. Considered asking Claude to generate questions from the corpus. Faster, but the ground truth would need a second pass and you lose the curator's judgment about what's a fair test. Hand-authored 30 — one afternoon's effort, no LLM bills, ground truth I can defend.
  • Eval output files: JSONL per-question + JSON summary. Two-file pattern is more verbose than one big nested JSON. Wins: JSONL is grep-friendly + line-streamable; summary is small + cheap to read for the UI; the two files can stay in sync because the summary contains the same per-question records inside by_qid.
  • Portfolio writeup format: extended README vs separate WRITEUP.md. Two docs splits attention. The README is the first thing a reviewer opens; investing in it directly is higher-leverage than maintaining a parallel writeup. Cross-references to implementation-notes.html (detailed decisions per phase) and followups.html (deferred items) live in the README for reviewers who want to drill down.
